## Gaps and uncertainty

- Offline for WellSky Personal Care: not found. Neither its product page nor its App Store listing mentions offline use.
- AxisCare offline: only the CEO interview mentions it. The mobile tutorial PDF, the caregiver app page and the features overview do not mention offline at all. Which exact items work offline is not listed.
- Photos offline (or at all): not found for any leader.
- Medication reminders offline: not found. AxisCare's [features page](https://axiscare.com/features/caregiver-mobile-app/) says the app can send medication reminders, but says nothing about offline.
- Which actions (clock in/out, tasks, notes) AlayaCare allows offline: its offline guides do not list them, so only the marketing page above supports notes and forms.
- Conflict handling (offline edit vs. server change) and automatic retry: not documented by any leader; AlayaCare's only instruction for failed uploads is to call support.
- The 12-hour expiry comes from one customer-hosted article and may be configurable.

## Dependency on the field-service queue

- The phone can only send these saves safely through the offline queue that the field-service session rebuilt on branch `cloud/fieldservice-depth` (commit 2350fa6: `apps/mobile/src/offline/engine.ts`, `README.md`, `OfflineContext.tsx`, `OfflineQueue.ts`, `useOfflineApi.ts`, tested by `tests/mobile/offline-queue.test.ts`; the waiting-list screen `apps/mobile/app/(details)/waiting.tsx` and `describe.ts` are on the same branch from another commit). That queue is not in this branch. Here `apps/mobile/src/offline/` still holds the older queue, which has no `recordKey` and no label.
- `apps/mobile/src/offline/` must not be edited from this PR. Any change to the queue belongs to the field-service session; this PR only relies on how it behaves.
- What fits already: each try of a queued save carries `Idempotency-Key: <the item's id>`, the same on every try (a UUID, or a fallback of letters, digits and dashes). Our server accepts 8 to 100 letters, digits and . _ : -, so those keys fit. The queue's README says the server does not look at the key yet; that is now untrue for two routes (medicine log and photo upload), and the README is the field-service session's file to change.
- Wiring still to do once the queue is merged, in `apps/mobile/src/care/components/VisitParts.tsx`: the task checklist (`PUT /api/care-tasks/time-entry/:id/:taskId`), the medicine log (`POST /api/medications/log`) and vitals must send through `useOfflineApi` with `recordKey` `visit:<timeEntryId>`, a label, and `savedAt` or `administeredAt` set to the tap time; and the "No signal" refusals there must go. A task save is a whole-value `PUT`, so repeating it is safe without a key. Vitals saves are not made repeat-safe yet.
- Photos: that queue is JSON only. Queueing a photo needs the picture file kept on the phone (`expo-file-system`, a native build) and an upload transport added to the queue, so photos cannot be done yet. The server's photo route takes the picture as a base64 text string up to about 5 MB.
- Free-standing visit notes have no phone screen to queue (notes live on tasks, doses and the clock-out note).
- Conflicts: a refusal (400, 409 and so on) comes back in plain words to the queue's "couldn't send - tap to fix" list; nothing is duplicated here.

## Status summary

- Built, hidden and marked not ready (`care_offline_saves`), server only: a medicine entry or photo sent twice with the same key is recorded once; the phone's tap time is the recorded time (future or older-than-30-days times are refused in plain words); a second caregiver's "given" for the same scheduled dose is refused naming who gave it and when; a dose of a stopped medicine is recorded and the office is told; the office's medicine record shows "Saved on the phone, sent <time>" on entries that arrived more than 15 minutes after they were given. 13 tests (`tests/homecare-depth-offlinesaves.test.ts`), written against the real server; I read them but did not run them.
- Left unbuilt: all the phone wiring (waiting on the field-service queue, above), photos from the phone, repeat-safe vitals, free-standing visit notes, download-ahead of the day's data, and the phone-call fallback. Nothing in this PR has been tried on a real phone, so none of the offline rows above is more than "the server is ready".
- Two weaknesses to know: the one-dose-one-record check reads then writes, with no database rule behind it, so two caregivers whose saves land at the very same moment could both be recorded (and it only applies when a scheduled time is sent); and the "Saved on the phone" label is shown for any entry created more than 15 minutes after it was given, including one the office typed in late by hand, so the wording can be wrong.
- The owner must verify by hand, after the queue is merged and the wiring is done: on a real phone in airplane mode, record a dose, tick a task, take a photo, then reconnect; check the office record shows each once with its tap time; try a second caregiver recording the same dose; and check what signing out does with saves still waiting.
