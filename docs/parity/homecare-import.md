## Gaps and uncertainty

- AlayaCare: no public help page on importing clients, employees, schedules or payers was found. Not found.
- WellSky Personal Care: only a marketing statement about customised onboarding was found; file format, mapping, preview, duplicates, undo are all not found.
- AxisCare: migration is described as staff-run via API. File format, field mapping, preview, duplicate handling, dry run and undo are not found. help.axiscare.com was blocked, so a self-serve importer may exist that this research could not see.
- Authorizations, certifications and payers/contacts as importable record types: no leader page confirms any of them. Only CareLineLive (contacts, training) and the AxisCare advice article (authorizations named generically) come close.
- Dry run as a separate mode: not found anywhere. The closest are preview-before-commit steps (CareSmartz360, ShiftCare, VisualCare).
- Undo/rollback: confirmed only for Healthy Roster (new records only) and SKED (via support, 30 days). No leader documents undo.
- Duplicate handling is documented only as key-based match-and-update (ShiftCare, CareLineLive) or skip (SKED). CareSmartz360, VisualCare and Birdie say nothing.
- Reference vendors are not market leaders; treat them as design patterns, not parity targets.

## Parity build, 10/31 — rows 8, 9 and 10
Status: **built**, behind three hidden feature ids (not ready until the owner has tried them in a real browser): `care_import_all` (row 8), `care_import_wizard` (row 9), `care_migration` (row 10), all on top of `care_import`.
- **Row 8, every record kind** (`core/importKinds.ts`, `core/importRows.ts` FIELDS): authorizations (client + payer by name, units, dates, status), caregiver certifications, client credentials, medicine lists (dose times, as-needed), pay rates (cents in, the rate columns' decimal out), payers, important contacts, billing history (past invoices in cents, the payment status derived from what was paid, billed to a payer or the family), training, leave, journal entries (dated at noon on the agency's clock), reviews (1–5 scores) and expenses. Each has a template with an example row, a parent found by name / email / our id / reference code (a name two people share is refused), a duplicate rule read from what is already here (`data/homecareImport.ts existingChildKeys`), and undo that keeps a record anything points at. Permissions are the area's own (`care-billing`, `care-hr`, `care-payroll`, `care-clients`). Test: `tests/homecare-parity-import-kinds.test.ts` (13).
- **Row 9, the wizard** (`core/csvImport.ts`, `core/importXlsx.ts`, `core/importZip.ts`, `core/importAttach.ts`): Excel .xlsx read without a library (shared strings, booleans, date cells as year-month-day; the sheet can be chosen); pasted tab-separated rows; a mapping saved under a name (`import_mapping`) and reused when the headings match; a date-format choice; a bad cell fixed on the preview (the error row carries its cells; the server re-reads the file with the fixes); "Update the records this file matches" on the fields the owner or an admin chose (`company.settings.importOverwrite[kind]`), counted as updated, the old values kept on the batch record (`import_batch_record.previous`) and put back on undo; the old system's reference code kept (`import_external_id`) and used to find the record next time, our own id accepted, name + zip before name; "custom:" columns kept as custom fields (`custom_field_value`; `GET /api/care-import/custom-fields/:entity/:id`); several payers in one cell as the client's payers in order; a zip of documents or qualifications attached in bulk with its own attached / skipped / failed summary and undo; the preview counts the plan's seats so the dry run predicts a full plan. Test: `tests/homecare-parity-import-wizard.test.ts` (18): the plan-seat refusal, the 2000-row and 2 MB limits and undo across two companies among them.
- **Row 10, assisted migration** (`core/migration.ts`, `office/migration.ts`, Factory `apps/api/src/unified/migration.ts`, platform `pages/MigrationPage.tsx`, agency screen `office/MigrationRequest.tsx`): the agency sends its export (up to 10 files, 20 MB each, kept in its own database) with a note and the old system's name; Twomiah staff, owner or admin on the platform's Migration screen, open the request, download a file, run the SAME importer on it (dry run, then for real, any kind, any date format, update-in-place) or attach a zip, see what was loaded (undo included), compare record counts old vs here (the agency types the old system's counts), tick the staff items of the sign-off checklist and set the status with a note the agency sees. The agency ticks its items and can cancel. Every Factory call is passed to the tenant's `/api/internal/care-migration` with its Factory key, only the migration paths, `by` stamped with the staff member's email; a tenant without `care_migration` refuses. Tests: `tests/homecare-parity-migration.test.ts` (8), `tests/unified/factory/migration.test.ts` (6). Staffing it is the owner's decision — the tooling waits for a request.
- **Not done / not seen:** not seen in a real browser (the tenant's Import and Assisted migration screens, the platform's Migration screen). Custom fields are kept and readable by API but no client / caregiver / payer screen shows them yet. The payers-in-one-cell split gives each payer 100% in priority order (the office sets the real percentages on Split billing). A re-import never renames a record (names and references find it). Compliance policies (`compliance_documents`, company-level) are not an import kind; caregiver compliance is covered by certifications, training and the qualifications zip. An .xls (old Excel) file is refused: save as .xlsx or CSV. The Factory's Migration screen lists unified home-care tenants only.

## Status summary

- Built (hidden behind `care_import`, not ready): a self-serve CSV import of clients, caregivers and recurring shifts with guessed column matching, a row-by-row preview, duplicate skipping, a dry run, a list of past imports and an undo that keeps anything already used. 18 tests are written in `tests/homecare-depth-import.test.ts`; they run against a test copy of the product, never real agency data (they were not run while writing this page).
- Imports only add. Nothing is ever updated, so re-importing a corrected file will not fix records already created. Updating would need the owner to decide which fields a re-import may overwrite, and an undo for those edits.
- Left unbuilt: authorizations, medicines, pay rates, certifications and documents; Excel files; saved column mappings; inline editing on the preview; custom fields; a staffed migration service. Each needs a file layout and a duplicate rule decided first; the migration service is the owner's call to staff.
- Written but untested: the plan-seat refusal for caregiver rows, the 2000-row and 2 MB limits, and undo across two companies. The dry run does not predict a full plan.
- The owner must check by hand: import a small real client file, a caregiver file and a shift file on a copy of a real agency, confirm the dates read the right way round (US month/day), then undo it. Check that a new caregiver cannot sign in until Reset password is used. The leaders' import tools were read from public help pages only; none were used, and AxisCare's help centre could not be opened.
